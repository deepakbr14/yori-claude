# Yori 10 Programs Contract

Status: authoritative, host-independent Programs platform contract. Canonical source: backend/contracts/programs_contract.md. Identical copies ship in the ChatGPT and Claude plugins.

## Independent application platform

Yori Programs are the primary application system: focused tools, games, visualizations, calculators, trackers and small shared applications hosted by Yori on Firebase. The AI host supplies reasoning and MCP calls; the same backend and separate Viewer execute Programs.

One creator owns canonical HTML and metadata at a permanent opaque program_id. Titles, slugs and version labels are editable metadata, never identity. Revisions preserve the ID, existing state keys and working behavior. A fork uses a new ID and copies authorized source and suitable metadata, never another Program's local state, shared application records, identities, observations, queued actions, receipts or Cortex meaning.

## Visibility and access

Every new Program chooses visibility: private (creator only), yori_users (any authenticated Yori member), or public (anyone, no login). New publications default to private when no choice was supplied. Existing Programs with missing visibility retain their historical public behavior. Revising an existing Program without a visibility argument preserves its current access.

Use publish_program visibility for creation. For later changes, read_program supplies settings_revision; use update_program_settings with expected_settings_revision and an idempotent request_id. The creator can also change visibility in Viewer → Programs. Widen visibility only when the user requests that audience. Server authorization covers standalone rendering, source reads, resolution, forks, old and new application endpoints. Guessing an ID never grants private access. Already downloaded copies cannot be remotely erased by changing visibility.

Public links run without sign-in. Restricted links show a source-free entry page; open from the signed-in Viewer, which supplies a Program-scoped token in the fragment. No OAuth credentials, passwords or general Viewer tokens are included in Program source. An unconnected visitor is directed to the existing Yori login, not a new app signup.

## Browser persistence

Use window.YoriProgram rather than inventing an account/storage layer. readState(), writeState(state) and watchState(callback) preserve the existing local state key yori:program:<program_id>:state and its revision. State is a JSON object subject to the browser’s existing storage quota; this upgrade does not impose a smaller save limit on existing device data. Existing custom local stores retain their keys and can continue publishing declared observations.

readProfile() and writeProfile({display_name, settings}) use a separate Program-scoped browser key. A name is at most 48 characters; the profile is at most 16 KiB. Names need not be unique and are not verified identities. Preferences, display names and saved progress survive reopening on that browser. Private browsing, storage clearing, another device or another browser can lose or separate those saves. There are no Program-specific accounts or registration. Neither the profile nor state is automatically sent to Yori or to shared storage.

## Bounded shared application data

Programs do not use Yori as general cloud application storage. They may opt into this deliberately limited service for shared leaderboards, scores, results and small declared records. Application records are separate from Personal/Shared Cortex memory and from expiring observations.

Keep manifest version 3 and declare shared_data.collections. At most four distinct collection names are permitted per Program, including retired declarations; renaming does not silently discard or bypass the storage bound. Reuse names, explicitly clear incompatible contents, or plan a separately authorized migration. Each collection has with 1–100 entries of at most 2,048 UTF-8 JSON bytes. A collection occupies one bounded document, capped at 256 KiB including bookkeeping. Entries require a closed object schema; close nested objects, bound strings and arrays, and use inline primitive/object/array types. Maximum nesting is four, objects have at most 24 fields, strings at most 1,024 characters, arrays at most 32 items. External references and executable schemas are rejected. Do not declare collections just because the capability exists.

Example embedded in <script id="yori-program-manifest" type="application/json">:

```json
{"version":3,"state":{"scope":"device","initial":{}},"shared_data":{"collections":{"scores":{"kind":"leaderboard","max_entries":50,"max_entry_bytes":1024,"order":"desc","schema":{"type":"object","additionalProperties":false,"properties":{"score":{"type":"integer"},"display_name":{"type":"string","maxLength":48}},"required":["score","display_name"]}}}}}
```

A leaderboard requires numeric score and display_name (at most 48 characters). order is desc for higher-is-better or asc for lower-is-better. The server keeps a participant's best result and only the configured top entries. A submission receipt confirms processing; retained=false means it did not remain in the top list. Casual scores are client-reported, not independently verified. Use textContent/escaped rendering for submitted names.

A records collection uses the same bounded schemas. It has numbered entry slots from 0 to max_entries-1. write_policy defaults to owner; participants can be enabled explicitly. A participant may create an empty slot or revise its own slot, not overwrite someone else's. The creator can manage any slot. Record writes require the current collection revision. This is not a private account database or an unrestricted document store; shared records are visible to everyone allowed to run that Program.

Browser API:

- await YoriProgram.sharedData.read('scores', {fresh:false}) returns bounded entries, collection revision and limits. Reads are cached locally for 15 seconds; fresh:true bypasses that cache. No automatic polling.
- await YoriProgram.sharedData.submitScore('scores', {score:42}, {request_id:'score_<unique>'}) uses the local profile name unless display_name is explicitly provided.
- await YoriProgram.sharedData.write('collection', value, {request_id, entry_id, expected_revision}) writes a declared entry. Use numbered slot/revision for records. Leaderboard submissions use a server-derived participant key.
- await YoriProgram.sharedData.clear('collection', {request_id, expected_revision}) is creator-only and requires the current revision. Clear is an explicit data operation, never part of publishing.

Reuse the identical request_id and payload after an uncertain failure. The most recent 32 write receipts per collection are replayed without another write or quota charge; older retries may fail revision checks. Do not pretend an unconfirmed write succeeded. Browser failures leave local progress intact. Public visitors receive a short-lived, Program-scoped anonymous capability stored in their browser; it creates no account or member profile. Authenticated visitors use their existing Program session. Anonymous identity can change when storage is cleared; sophisticated anti-cheating is outside this release.

Server checks current visibility, declarations, source hash, write policy, schema, byte limits, revisions and quotas. Data/permission changes and retries are transactional. Quotas per Program: reads 120/minute and 6,000/day; writes/clears 30/minute and 1,000/day; anonymous session minting 10/minute and 200/day. UTC windows apply. The backend rejects over-limit operations with program_rate_limited; stop retrying until later. There are no paid model/embedding calls for this service. A cold operation uses three bounded transactional document reads and one budget write, plus one collection write for mutations (and a one-time registry write for older Programs); visibility/auth routing may add a Program lookup. No collection-wide scan or continuous data listener is required. Failed hostile requests can still consume infrastructure resources; these limits are not a claim of free or unlimited public hosting.

The creator can pause/resume shared data and explicitly clear a collection in Viewer → Programs. Pausing preserves stored data and local saves. The creator may still inspect/clear while paused. A changed collection definition does not reinterpret or erase old data: incompatible schema hashes are rejected until an explicit creator clear or a separately approved migration. Yori can use read_program_shared_data for authorized declared records, never as a route to private browser state. It does not trigger Cortex learning.

## Supported boundaries

No Program-specific signup, accounts, registration, invitation roles, private user database, arbitrary Firebase access, payments, secrets, scheduled jobs, automatic model turns, arbitrary persistent blob storage or unbounded cloud storage is added. Explain unsupported requirements and discuss an explicit platform extension or external service if needed. Do not migrate or delete existing external applications or legacy Program records without a separate request. Program deletion removes its server descendants, including shared_data and shared_runtime, but cannot erase users' browser storage or already copied source.

## Yori actions

A Program may declare typed `yori.actions` so Yori can perform meaningful operations through chat. Each action needs a clear purpose and a closed JSON argument schema. Declare only operations that alter or inspect the Program's subject matter, such as making a game move, applying a filter, or recording a supported item.

Do not declare cosmetic or redundant commands such as `open`, `refresh`, `reload`, or `show`. A user can open or refresh the Program directly, and such commands give Yori no useful agency.

An accepted action request proves only that the service queued it. The owner opens the Program from Viewer → Programs; that owner-scoped runtime leases the action, invokes the matching handler, and acknowledges success or failure. The completion may include a bounded JSON result describing what the open Program actually did or observed. This result is an operational receipt, not persistent application state. The open owner Program receives actions automatically. Do not claim execution until `run_program_action` or `check_program_action` reports `executed: true` with completed status. Pending or leased is not execution, and a failed acknowledgement is not success.

The MCP bridge transports the selected argument object as JSON text in `args_json`. The backend parses that text as exactly one object, then validates it against the selected Program action's `args_schema` before queueing. This transport does not weaken or replace the typed manifest boundary.

## Automatic interaction and current observations

An owner-authorized open Program may share one current observation with Yori. Declare exactly what can be shared in manifest version 3 under `yori.observation`:

```json
{"description":"Current selected task after Apply", "max_bytes":4096, "ttl_seconds":600,
 "schema":{"type":"object","additionalProperties":false,
           "properties":{"revision":{"type":"integer","minimum":0},
                         "selection":{"type":"string","maxLength":200}},
           "required":["revision","selection"]}}
```

The root schema must be a closed object. Bound strings and arrays and close nested objects where appropriate. `max_bytes` is 1–8,192 UTF-8 JSON bytes; `ttl_seconds` is 60–600 seconds. Use a smaller cap when sufficient. Never share complete application history, credentials, private Cortex content, files, or an arbitrary state dump. This current operational view expires; it is neither durable cloud application storage nor automatic Cortex learning.

The reusable browser API is `window.YoriProgram`:

- `await readState()` and `await writeState(state)` read/save device-local state. Keys preserve the permanent Program ID. `watchState(callback)` reacts to local changes without server polling.
- `await apply(state, observation)` saves local state first, then shares the declared observation. If sharing fails, local state remains saved and the UI must say it was not shared.
- `await publishObservation(observation)` shares a declared view after a Program saves through its existing local store. Use this when preserving an established game/state key.
- `onObservation(() => currentBoundedView())` supplies the current view when the owner opens the Program and after a Yori action. It never uploads undeclared data.
- `onAction(name, async (args, state, context) => ...)` registers a typed handler. A plain returned object is saved locally and becomes the bounded result. Alternatively return `{state, result}`; an omitted state preserves existing device data. Throw on a failed operation. Do not return success before saving it.

When a user selects or previews an operation, do not apply or publish it yet. Apply commits it locally and shares the committed view. Keep selection-before-Apply where requested. Validate domain revisions in the action handler as well as at the service boundary; for example, verify a game's ID, revision, turn, and legal move. A returned result reports the action actually performed.

In chat, resolve and read the canonical Program first. If it declares an observation, call `read_program_observation`. Read the current board or tool view and choose typed arguments from that evidence. Supply its exact `observation_id` in `run_program_action`; do not ask the user to copy state or retype the action. “Your turn” is resolved against the ongoing visible Program context. The service rejects expired or replaced observations and old source revisions. Do not repair a retrieval failure by inventing a board.

The Program receives actions through a single owner-scoped Firestore notification listener while open. The browser receives only a wake-up ID; the authenticated backend leases the action and validates its owner, source, tab, and observation. No manual Refresh and no automatic model turn are needed. Public visitors may use the local Program, but cannot inspect owner observations or receive owner actions.

`run_program_action` waits up to eight seconds for acknowledgement. A pending/leased result is not success. If still pending, use `check_program_action` for that same action ID; never queue a duplicate move. Closed, disconnected, expired, and stale tabs have explicit unconfirmed/failure results. Reopen the owner Program when needed. Requests expire after five minutes. Closing a tab disconnects it where the browser can send that notice; a crashed tab may instead remain unconfirmed until expiry. Never infer execution from connection state.

Request IDs are idempotent for identical actions. A local execution journal and browser lock prevent replay on duplicate delivery; finished receipts are retried without repeating the handler. If a tab crashes during a handler, the outcome is uncertain and the handler is not blindly repeated. Local execution with a failed acknowledgement is also unconfirmed. Reconcile the actual current view before a fresh action. Exactly-once arbitrary JavaScript across crashes is not promised.

Firestore stores one bounded current observation, expiring tab/control/wake-up records, and bounded action receipts under the existing Program identity. Expiry is enforced when reading/acting; asynchronous TTL deletion performs later physical cleanup. Program deletion removes these descendants. These operational records remain separate from declared shared application data. No general browser database authority is introduced.


## Creating reading revising and forking

Resolve a named Program with resolve_program before acting. Prefer owned exact matches; ask if the bounded candidate list is ambiguous. read_program returns authorized canonical HTML, normalized manifest, source_sha256, visibility and settings_revision. Reading source is not authority to revise it.

Create with a fresh request_id and no program_id; choose visibility. Revise with the exact existing program_id and complete source, preserving local keys, manifest actions/observations and intended shared-data schemas. Source publication does not implicitly clear shared records or change existing visibility. Fork without program_id and with forked_from plus the exact forked_from_source_sha256 returned by read_program. Read again if that parent changed. Never guess IDs or claim a copy of someone else's local or shared state.

Inspect actual live observations before choosing typed actions. Queue persistence, source publication, shared-data persistence, browser execution and Cortex learning have separate receipts and meanings. Preserve the established observation/action protocol above, including source/observation revisions, owner-only tabs, idempotent delivery and acknowledgement. ChatGPT and Claude expose the same tools and argument contracts.

After publication say it is available in Viewer → Programs. Provide a direct link when asked; public links need no login. Browser-local saves and a shared leaderboard are different stores: a result can save locally while a shared submit fails. Explain that distinction accurately.

## Later conversions from external applications

Selected existing applications can later be converted into Programs using their actual source, assets and authorized data exports. Prepare an inventory, canonical identity mapping, local-state key plan, declared shared schemas, data limits, privacy/access choices, validation and preservation of the original application until acceptance. Preserve the original application until a separately authorized import and acceptance test succeeds. Conversions require a separately authorized, validated import; publishing platform code never imports application records. Neither host can implicitly see another host's files or native application state.


## One current multi file application

Keep `publish_program` for small, complete single-HTML applications. Larger applications have one current immutable file manifest with `index.html` plus JavaScript, CSS, images, fonts, audio and static JSON/text/CSV. Source assets live in the dedicated private application object bucket configured by YORI_PROGRAM_BUNDLE_BUCKET, behind the same Firebase Hosting domain/CDN. Firestore holds a small manifest, hashes and current application pointer, never the dictionary or full bundle. No new always-on service is required.

Yori normally sends exact source text through write_program_file and assembles it with stage_program_files. Read exact unpublished text through read_program_file. Use read_program_assets and reuse_program_asset for verified server-held dictionaries, approved static data and authorized existing Program assets. Use direct source tools for every multi-file workflow. ZIP-transfer tools, downloaders, UI handoffs and upload endpoints have been retired. Content-addressed storage skips unchanged objects. Limits: 32 MiB total application files, 64 files, 8 MiB/file, entry HTML 256 KiB, manifest 24 KiB. There is no retained application-version limit or history. Relative safe paths only; no traversal, executable server files or active SVGs. Bundle JavaScript has the same browser sandbox/permissions as single-file Programs, never database credentials or server execution authority.

`read_program` reports `source_mode`, bundle inventory and the canonical revision hash. For bundles, its HTML is a small **revision launcher**, not complete application source. Use `read_program_bundle_file` for one UTF-8 file, at most 16,000 characters/page; binary assets remain references. Never replace a bundle with its launcher. `publish_program_bundle` accepts an already staged `bundle_version`, current `expected_source_sha256` and stable `request_id`. Publishing is creator-only, source-revision checked, transactional and idempotent using eight bounded idempotency receipts that contain no historical file manifests. No historical application can be reactivated for rollback. bundle_version is a compatibility field containing the internal staging/content fingerprint, not a retained application release. `fork_program_bundle` copies only the currently authorized inspected application files to a new private-by-default Program; it never copies game records or another player's state. Existing single-HTML source/fork APIs remain available.

`YoriProgram.assetUrl(relativePath)` returns a manifest-verified content-addressed URL. Public immutable assets cache for a year; private/member assets require the current authorized session and return private/no-store. Current visibility is checked on origin requests. Previously public downloaded/CDN-cached copies cannot be instantly revoked by later making a Program private. Never publish secrets. Initial HTML is no-store so the current application is selected on reopen. Shared collection declarations and existing local keys must be preserved during revisions; incompatible migrations require explicit authorization.

`YoriProgram.storage.getItem/setItem/removeItem` provides synchronous Program-ID-scoped compatibility keys. Prefer existing readState/writeState/profile for new structured state. No existing state keys are renamed. Cross-origin application storage cannot be silently read; importing an old browser identity requires its original capability, never a guessed nickname.

## Approved deterministic game submissions

A leaderboard declaration may opt into an installed trusted validator, initially `validator: "daily_word_grid_v1"`. This is a small server-code registry, not uploaded server code or an extensible execution framework. Generic sharedData read/write/clear rejects validator collections with validated_submission_required. Their history cannot be cleared through a casual leaderboard API. Creator pause/resume still works.

Use `const game=YoriProgram.game('daily')` for read({fresh:false}), check(board), submit(board,{request_id}), and rename(name). Reads cache for 15 seconds; no server polling. Submissions contain the current date, rulesVersion, twelve null-or-{x,y} tile positions and nickname. The server derives letters, daily tiles, bonuses, dictionary membership and scores; client claims for scores, words, multipliers or player IDs are rejected. Persistent player capability stays browser-local; the server stores only its SHA-256 identity. The browser's optional linkLegacyPlayer(raw) requires the actual old 64-hex capability. No registration, nickname-based impersonation, or silent account linking.

The approved daily word-grid validator preserves the pinned reference rules for daily generation, 7-square rules and older 8-square history, Chicago midnight/DST, crossing/multiplier order, best-score-only boards/timestamps, score-time leaderboard ties and tied daily championships. Public reads expose only bounded current standings/championships and completed-day winning boards. Open competitors' layouts and raw player capabilities are never returned. The validator/dictionary performs no AI or embedding calls. Local browser validation remains instant; trusted compute is used for explicit checks/submissions and bounded scoreboard reads.

`read_program_game`, `check_program_game` and `submit_program_game` provide the same approved game workflow to ChatGPT/Claude. Only the creator can use the retained `agent:yori` competitor. Read returns puzzle letters/bonuses, Yori's own previous board and public scores, not a reference solution. Yori must construct her own legitimate board, check it and submit with a stable request ID; never derive an entry from hidden seed layouts or another player's live board. These operations require no open browser. A browser `place_board` typed action changes only the owner's local board and must not be described as a competitive submission.

Validated history is separate from Cortex and generic shared records: bounded documents under programs/{id}/validated_games/{collection}/game_days/{Chicago-date}. Limits: 100 entries/day (or lower declared cap), 512 lifetime participants, 3,650 scored days, 256 KiB/day, aggregate 384 KiB, up to four pending scored-day finalizations per request. No automatic deletion/archive/reset at limits; fail clearly and request owner-reviewed archival. Finalization is lazy and idempotent; no cron or continuous listener. Existing shared-data quotas apply across read/write/session operations. Recent 64 submission/rename receipts per day replay without writes; best-score-only changes and finalized-day markers prevent repeated scoring/win awards beyond that replay window. Queries use fixed document IDs; data fields are excluded from indexing and have no TTL.

Historical imports are administrative, validated and atomic, with exact source archive/row hashes and retained original identifiers. Existing conflicting data is rejected, never overwritten. Preserve old scores/boards/timestamps even if current rules flag them; record the discrepancy in a separate audit rather than silently rescoring. The original application remains unchanged until a separate acceptance/cutover decision.


### Provider independent source workflow

For a small complete single-HTML Program, publish_program remains the simplest path. For multiple files, resolve/read the existing Program first, or create its permanent identity through publish_program if genuinely new. Preserve the current source hash for the later publication check. Do not replace an existing Program with a new ID.

write_program_file accepts program_id, safe path, exact text and optional append_to_sha256. A call writes at most 64 KiB of UTF-8; complete files are bounded to 8 MiB. For longer source, use the previous returned hash for each append. Identical append retries return the identical result instead of appending twice. Separate branches produce independent immutable hashes; there is no globally mutable draft or cross-conversation current-file pointer. Partial JSON is allowed while writing but must be complete at staging. Text file bytes live in the existing private object store, never Firestore or Cortex. Returned stored=true and pf_ receipts establish only stored file bytes, not a validated or published Program. read_program_file reads exact owned object bytes by hash in 16,000-character pages, including unpublished files. Existing read_program_bundle_file reads active published files.

read_program_assets returns approved reference asset IDs, exact source hashes/formats/sizes and the active Program inventory. reuse_program_asset copies either an approved asset_id or a precise authorized source_program_id/source_version/source_path into the destination Program, returning its exact hash. The initial catalog uses the already approved ENABLE dictionary (152,405 entries) and original puzzle seeds; the source hashes are verified against existing validator provenance. Adding future assets requires an explicit backend catalog change, never arbitrary server paths or user-uploaded executable code. Other users’ unpublished or private source files cannot be copied. Public or member-visible assets may be copied only from the currently published authorized version. The original asset, game history and private browser state are unchanged.

stage_program_files accepts one to 64 {path,sha256} references already stored in this exact owned Program. Optional base_version must identify the currently active application and applies replacements plus explicit remove paths. It never removes the current index.html, scores or Cortex data while staging. Unreferenced old source files are removed only after successful activation and upload/staging protection checks. The server verifies every file’s actual bytes/hash, safe path, size, complete JSON, SVG safety and the existing HTML/manifest/security contract before marking the version ready. File sizes, browser sandbox, visibility and serving rules remain unchanged. There is one current application; at most four temporary staging candidates expire after two hours. Direct staging reuses the verified existing objects rather than sending or re-uploading assets. publish_program_bundle then activates that version using the current expected_source_sha256 and stable request_id. Publication remains atomic, owner-authorized, concurrency checked and idempotent; no file operation activates a version automatically.

The host LLM interprets supplied material and sends the important source/data it can actually establish. Do not require a transferable ChatGPT attachment ID or Claude Artifact. Never claim byte-exact copying of a file the host could not read. Preserve exact assets by server-side reuse rather than reconstructing dictionaries, images, music or other large exact datasets from model guesses. No routine operation calls an LLM, embedding service or external file downloader on the backend.

Cost bounds: existing per-Program quotas (30 writes/minute, 1,000/day; 120 reads/minute, 6,000/day) apply across these operations. Direct file writes add at most 32 MiB of new text/copied/binary bytes and 1 GiB of materialized intermediate file writes per Program per UTC day. Appending charges the new chunk toward the first limit and the resulting immutable file toward the second. Intermediate objects are immutable and protected by two-hour upload leases. After publication, bounded garbage collection removes unreferenced source objects and obsolete staging documents. An hourly queue worker also cleans expired abandoned uploads without needing another deployment. Firestore stores operational metadata, not file bytes. program_asset_gc is a server-only queue with a single-field next_run query; bundles.purge_at expires temporary staging and programs.bundle_staging is unindexed. No new composite index, client rule, bucket, secret, external provider or always-on service is needed. Server authorization and the existing private bucket remain mandatory. A valid but unused written object is not a published asset and is not publicly served.

For narrow edits to an active bundle, stage_program_bundle_patch remains supported; direct file writing plus stage_program_files works for both initial assembly and later edits without retransmitting unchanged assets.

For a separately requested migration, preview_program_history_import checks up to 1,000 exact original approved-game records (512 KiB/request), ownership, current Program revision, installed validator and scoring exceptions. import_program_history performs the atomic initial import and returns an idempotent receipt. Both require the real source metadata and its supplied archive SHA-256; the service computes/verifies the submitted rows hash, and explicitly does not pretend to have verified an unavailable source archive. A conflicting existing game is rejected, never merged/erased. No application source, original Site or production records are migrated by deploying this platform upgrade. Yori must carry out any later application conversion only from a separate owner instruction.


### Retired external file transfers

Only direct source writing, exact server-side asset reuse and immutable publication are exposed. No external-provider file download or ZIP-transfer interface remains callable. The existing manifest/serving format, internal content fingerprints, single-HTML publishing and owned text-file patching remain supported. Application history and rollback are removed. A multi-file application is not a ZIP transfer. Previously published applications and stored data require no conversion.


## Exact binary assets

Use `write_program_binary_file` for original PNG, JPEG, WebP, GIF, ICO, MP3, WAV, OGG/Vorbis/Opus audio, WOFF and WOFF2 files. The server accepts only the documented static formats, not arbitrary executable files. An extension alone is insufficient. Files remain at most 8 MiB; complete applications remain at most 64 files and 32 MiB.

The host must have an authorized byte reader and encoder, such as its code execution environment. Read the actual original file bytes, calculate SHA-256, and Base64-encode each byte slice with code. Never guess bytes, fabricate encoded content, regenerate an image in place of copying it, or treat a host file ID as transferred data. If the host cannot expose the original bytes, explain that limitation; this MCP capability cannot grant access to an inaccessible attachment. No provider file-transfer component, download URL, ZIP, or manual Viewer transfer is involved.

All calls carry the exact owned program_id:

1. `operation: begin` with a stable request_id (8–100 ASCII letters, digits, underscores or hyphens), safe path, total_bytes, expected_sha256 (64 lowercase hex digits). The server binds these values and returns upload_id, status, next_offset and chunk_bytes=49152. Reusing request_id with different intent is rejected. An already stored identical validated asset can return complete immediately without transferring chunks.
2. `operation: chunk` with upload_id, offset in original bytes and canonical padded data_base64 (maximum 65,536 characters, 49,152 decoded bytes). Use full chunks except the last; at most 192 chunks per file. The offset must match next_offset. Identical chunk retries are acknowledged without appending or charging twice; conflicting bytes at the same offset fail. Chunk receipts are not a complete-file receipt.
3. `operation: status` with upload_id resumes from next_offset after an uncertain response. `operation: abort` closes only an unfinished upload; it does not delete a Program or published asset. Maximum four active uploads per Program, two-hour expiry, at most four retained finished/aborted upload records. Expired or evicted operational receipts require a new begin request; immutable completed assets can still be reused by hash.
4. `operation: finish` with upload_id assembles contiguous stored chunks and checks total length, original SHA-256 and bounded format/container validity before returning stored=true, sha256_verified=true, content_type and the existing pf_ file receipt. The browser remains responsible for actual decoding; format checks are not malware certification. Repeating finish returns the same receipt. Invalid or incomplete bytes never become a ready version.
5. Pass the finished path/sha256 pair to stage_program_files along with the application’s other files. Staging revalidates every asset. Publish separately through publish_program_bundle with the current expected_source_sha256. Storing, staging and publication remain distinct. Public immutable delivery serves exact bytes with the validated content type, nosniff and hash-based cache keys; private access checks still precede delivery.

Quota and storage details: existing 30 writes/minute and 1,000/day per Program apply to begin, newly reserved chunks, first finish and abort; status/finish checks use existing 120 reads/minute and 6,000/day. Respect returned rate-limit errors and retry times instead of spinning. Large uploads may need paced continuation. New chunk bytes count once toward 32 MiB/day and intermediate storage; final assembly additionally counts its length toward the existing 1 GiB/day materialization cap. Base64 expands transport by about one third and may consume host context/tokens; there are no AI or embedding calls in storage or serving. Identical chunk/final objects are content-addressed within the Program. Intermediate chunk objects are protected until the upload expires; unreferenced ones are cleaned afterward. Abort closes an upload without deleting the active application. Existing whole-Program deletion removes its complete object prefix.

Binary sessions reuse one bounded programs/{program_id}/runtime/binary_uploads document. Only metadata, hashes and offsets live in its unindexed response field; raw/Base64 content lives solely in the existing private asset bucket. purge_at uses the already configured runtime TTL (two-day ledger retention; the application enforces the shorter two-hour upload validity). Server transactions reserve quota and upload state together, with immutable object writes between reservation and acknowledgement so interrupted writes resume safely. The source lifecycle additionally uses the program_asset_gc queue, an hourly scheduled worker and bundles.purge_at TTL. No new composite index, client rule, bucket, secret, model service or continuously running process is required. Existing runtime.response index exemption and runtime.purge_at TTL must remain deployed. No Program identity, visibility, browser state, score or Cortex data is changed by beginning or finishing an upload.


## Current application source lifecycle

A Program has exactly one active application. Its stable Program ID and public URL do not change. The internal content fingerprint is used for integrity, caches and concurrency; it is not application version history. Staging and publication stay separate. At most four owner-scoped staging candidates may exist for two hours, each bound to the source revision inspected when staging began. Publishing replaces the active manifest atomically and invalidates all candidates based on the previous source. The temporary source record is not retained as history. Reusing a base or source asset requires the current application, even for its owner. Forking copies current files to a distinct new identity; it cannot recover previous applications or copy scores.

Cleanup occurs only after successful publication. Current files, valid stages, accepted binary chunks and reserved direct file hashes are protected. Two-hour file leases and object-age checks protect in-flight/abandoned transfers; existing unleased legacy uploads receive a one-time two-hour migration grace interval. A short per-Program cleanup lease fences writers and staging/publication while deletion runs. Object deletion is generation-conditional. Unknown document schemas are left untouched. Only recognized source/staging documents in programs/{id}/bundles and unreferenced objects in that Program's private object prefix are eligible. Player records, leaderboard history/imports, local browser data, identity, ownership and settings are never cleanup candidates.

Each pass scans at most 512 objects and 100 staging documents. Bounded post-publication cleanup failures do not reverse or misreport a successful activation: the persistence receipt remains valid and cleanup is reported separately. A server-only program_asset_gc queue schedules continuations and expiration work. An hourly Firebase scheduled function processes at most ten due Programs, without scanning every Program or invoking a model. At rest, it performs one bounded empty queue query per run; queued work costs only operational reference reads and eligible object/document deletions. There is no Viewer-wide polling or always-on service.

Deploy the backend's scheduled worker as well as the API. The established code/deploy.sh configures bundles.purge_at TTL and the bundle_staging index exemption before deployment. Existing broad client-deny Firestore rules also protect the queue. Old version lists and recognized stored source manifests are removed by publication/cleanup; no live migration runs merely by editing or packaging source. The operator command code/tools/cleanup_program_assets.py defaults to read-only inspection and requires --apply for live legacy source cleanup. Never claim old cloud objects were deleted unless that cleanup actually ran.


## Owner authorized application data administration

The generic tools describe_program_data, list_program_data, export_program_data, preview_program_data and manage_program_data administer logical application records. They share the same callable schema and backend on ChatGPT and Claude. Every operation verifies the exact authenticated Program owner inside its transaction. Public visitors, other members and browser Program-session tokens have no administrative authority. No open tab is needed. This interface cannot read browser-local saves, source/asset files, credentials, platform records, Cortex or another Program's data. A local save must be explicitly transferred before it can become server data.

Begin with describe_program_data. Ordinary declared shared collections expose entity records using their declared schemas and slot IDs or existing leaderboard IDs. Trusted daily_word_grid_v1 collections expose results partitioned by exact day, championship_starts, and read-only derived players and days. List days to discover available result partitions; do not scan arbitrary database paths. Existing Program-wide JSON storage exposes collection legacy; list its original keys, then read or manage one key. Undeclared retained shared collections can be inspected or pruned, but new records require a restored valid schema. Unknown storage engines require an explicit internal adapter, never arbitrary Firestore access.

list_program_data and export_program_data return logical id/data records, an opaque data revision and bounded next_cursor pages. Export format is yori_application_records_v1. Finish all pages before claiming a complete export, and export each desired game day separately. The revision covers the current application contract and authoritative data, including trusted-game metadata. Cursor revisions reject changed data. Records with large data may need a smaller page; the response cap is 128 KiB.

For owner-requested work, inspect records, prepare explicit changes and call preview_program_data before migrations or bulk changes. Preview is read-only, returns changed-record counts, proposed changed records and derived standings effects, and needs the expected_revision from the inspected entity. It is not an approval-token exchange. An explicit natural-language owner instruction authorizes the requested routine work; do not ask for another approval phrase or conversation turn. For consequential deletion or replacement, make sure it falls within the owner's requested scope.

manage_program_data accepts the same changes plus a stable 8–100 character request_id. Each change is {id, operation: put|delete, data?}; put sends a complete record, delete omits data. Use policy merge to preserve unmentioned records, or replace_partition only for explicit replacement of this entity or exact game day. Never resolve conflicts by emptying existing data. Set classification to owner_correction or imported_historical and include source.description plus optional reference/sha256. Source hashes are supplied references, not proof that the backend fetched an archive. A scoring exception preserves its original supplied score, board and achievement timestamp; owner writes never claim verified competitive submission.

Batches contain 1–50 changes and at most 128 KiB. Existing per-Program write quotas and authenticated MCP quotas apply. Each batch is one atomic transaction. Unrelated partitions remain untouched; one successful batch is not rolled back because a later batch conflicts. Reinspect affected records on revision_conflict, which includes the current revision and count. Identical request IDs replay compact persistence receipts for the last 64 administrative requests; a reused ID with a different payload fails. Keep receipts until the operation is confirmed. These receipts are an audit ring, not application version history. Replayed summaries preserve persistence, affected counts and revision but may omit the original per-player derived-change list.

### Trusted game starting totals and corrections

Use championship_starts to import absolute championship totals by the original user_id, never by nickname. Each record contains user_id, name, wins, through_day and last_win; through_day must be a completed Chicago day and positive totals need a last-win date. The total already includes all original wins through that cutoff. The adapter verifies overlap with existing finalized results, adds only the missing historical offset, preserves every existing result and adds later wins normally. Stored overlap_wins and administration are backend-derived metadata; do not manufacture them. Removing a starting total removes only its unrepresented historical offset, not result-based wins.

Result records retain day, user_id, name, score, board and achieved_at. Editing or deleting finalized results adjusts tied winner totals, last-win ordering and finalization bookkeeping atomically; editing today's open result leaves finalization to the existing Chicago rollover. No historical score is silently recalculated. Corrections under an imported cutoff change its overlap bookkeeping, not its already-covered absolute total. A total below existing covered wins is a conflict. Exact overlap/last-win reconciliation is limited to 32 finalized day documents; larger reconciliation fails without writes and needs a bounded archival adapter. This is a deliberate cost/safety limit, not permission to clear history.

The existing runtime game(collection).linkLegacyPlayer(originalToken) requires possession of the exact 64-character legacy capability. It preserves the original guest identity hash on subsequent requests. Names alone never prove linkage; admin tools neither expose those raw capabilities nor create a nickname-based link. Normal anonymous and competitive APIs retain dictionary validation, best-score rules and existing permissions. Browser leaderboard caches may retain their existing 15-second lifetime; use game.read({fresh:true}) for a deliberate fresh view, not continuous polling.

Platform deployment does not authorize an application migration. Daily Dozen's actual starting-total import and original external application remain for Yori to manage only when its owner requests it.
